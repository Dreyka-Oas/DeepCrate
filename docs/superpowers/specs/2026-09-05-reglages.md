# Les réglages de DeepCrate

Le mod n'a aucun fichier de réglages. Cinq nombres décidés dans le code gouvernent ce qu'un coffre
retient, jusqu'où il grandit, ce qu'une trémie peut y pousser et comment un compte est écrit à
l'écran. Cette fiche décrit la couche qui les sort du code, dans le format que le gabarit impose, à
l'adresse que le gabarit impose : `config/oas/deepcrate.json`.

Le gabarit est `/run/media/dreykaoas/O.A.S/projects/.claude/skills/mod-blueprint/reference/config.md`.
L'implémentation de référence, du même auteur et complète, est
`/run/media/dreykaoas/O.A.S/projects/mods/LethalBreed/mod/src/main/java/oas/dreyka/lethalbreed/config/`,
42 fichiers. DeepCrate a cinq options là où LethalBreed en a plus de trois cents, donc la couche est
plus petite, mais le chemin de lecture et d'écriture est le même et les écarts sont nommés un par un
plus bas, chacun avec sa raison.

## Ce que le code décide aujourd'hui

Le plan de l'audit ouvre sa tâche 7 sur six nombres qui se discutent sur un serveur
(`docs/superpowers/plans/2026-09-05-deepcrate-audit.md:759`) puis n'en nomme que quatre, aux lignes
780, 874 et 910 : la phrase promet deux options que le reste de la tâche ne dit nulle part. Les quatre
nommés tiennent. La lecture des sites d'appel en a donné un cinquième du même genre, deux candidats
écartés plus bas avec leur raison, et une poignée d'autres qui ne sont pas des réglages du tout.

### La contenance de base

`mod/src/main/java/oas/dreyka/deepcrate/api/DeepCrateApi.java:22`, `BASE_CAPACITY = 64`. Trois
lectures : la ligne 163, où `capacityOf` la rend pour une pile qui n'est pas un module ; la ligne 172,
où `capacityAmong` s'en sert de plancher ; et
`block/DeepCrateBlockEntity.java:36`, où le coffre naît avec neuf cases à 64 avant que son bloc soit
connu.

Un propriétaire de serveur peut vouloir autre chose, et pour deux raisons opposées. Il peut vouloir
que le coffre nu vaille déjà mieux qu'un coffre du jeu, sans obliger à fabriquer un module. Il peut
aussi vouloir le contraire, un coffre nu identique à un coffre du jeu même avec un pack de modules
généreux ajouté par un autre mod.

Aux extrêmes. En dessous de 1, `CrateStorage.requirePositive`
(`inventory/CrateStorage.java:287`) lève une exception dans le constructeur, et ce constructeur tourne
à la ligne 36 du bloc entité : chaque coffre chargé casse son chunk. Au-dessus de 32767, la case de
données qui porte la contenance jusqu'au client déborde ; `javap` sur le jeu de base le confirme,
`ClientboundContainerSetDataPacket` fait `writeShort` et `readShort`. À 32767 exactement, rien ne
plante mais les trois modules livrés ne servent plus à rien, puisque `capacityAmong` part de la
contenance de base et prend le maximum ; et un coffre d'écho cassé lâche 216 fois 32767 objets
découpés en piles de 64, soit environ 110 000 entités objet sur un bloc, contre 1728 pour le même
coffre à 512.

### Le comportement avec lithium

`api/DeepCrateApi.java:40`, `AUTOMATION_LIMITED = FabricLoader.getInstance().isModLoaded("lithium")`.
Une lecture, `inventory/CrateStorage.java:77`, dans `automationCapacityFor`, appelée par
`DeepCrateBlockEntity.getMaxStackSize(ItemStack)` que la trémie interroge case par case et tick par
tick. Deux lectures encore dans le gametest de trémie, aux lignes 36 et 69.

C'est la seule des cinq qui n'est pas un nombre mais une règle, et c'est celle qu'un propriétaire de
serveur voudra le plus discuter, parce qu'elle lui coûte la fonction principale du mod. Le mod décide
aujourd'hui pour lui : lithium présent, l'automatisation s'arrête à 64. Quelqu'un qui ne fait pas
tourner de trémie contre ses coffres, ou qui accepte le risque en connaissance de cause, n'a aucun
moyen de revenir dessus.

À l'extrême, il n'y en a qu'un : mis à `false` avec lithium installé, la destruction mesurée revient,
huit blocs de terre par passage. Le README le dit déjà aux lignes 95 à 99 et la page de boutique le
dit en encadré rouge. Le réglage ne change pas ce fait, il en rend la décision à celui qui tient le
serveur.

### Les rangées par page

`api/CrateLayout.java:10`, `MAX_ROWS_PER_PAGE = 4`. Une lecture, la ligne 13, dans `balanced`, que
`DeepCrateApi.layoutFor` appelle à l'ouverture du coffre et en repli quand la découpe d'un addon ne
couvre pas les rangées.

Un propriétaire de serveur peut le vouloir à 6, pour qu'un coffre de six rangées ou moins tienne sur
une seule page et ressemble exactement à un grand coffre du jeu. La découpe est calculée côté
serveur, dans `getScreenOpeningData` et `createMenu`, et voyage dans `CrateOpenData` : le réglage du
serveur s'applique donc à tous ses clients, y compris celui qui joue dans une petite fenêtre.

Aux extrêmes. À 1, chaque rangée devient une page : un coffre d'écho à seize modules de rangée en
donne vingt-quatre. `DeepCrateScreen.init` empile les boutons de page quatre par colonne à droite du
panneau, soit six colonnes, soit 108 pixels au-delà d'un panneau large de 176 ; sur un écran virtuel
de 320 de large, les derniers boutons sortent par la droite. Au-dessus de 6, la hauteur de l'écran
est `114 + rangées * 18` (`client/screen/DeepCrateScreen.java:72`), donc 240 pixels à sept rangées,
là où le plus grand coffre du jeu s'arrête à 222 ; l'inventaire du joueur commence à passer sous le
bord bas, et les boutons de tri, dessinés au-dessus du panneau, sortent par le haut. Le plafond est
donc 6, pas davantage : la pagination existe précisément pour que le mod n'ait jamais à dessiner plus
haut que ce que le jeu de base dessine.

### Le seuil d'abréviation

`client/screen/DeepCrateScreen.java:47`, `ABBREVIATE_ABOVE = 999`. Deux lectures, la ligne 265 dans
`renderSlot` et la ligne 281 dans `getTooltipFromContainerItem`.

C'est le seul des cinq qui se lit sur la machine qui dessine. Un joueur qui joue à petite échelle
d'interface veut peut-être abréger plus tôt ; un joueur qui joue en 4K veut peut-être ne jamais
abréger, et lire ses 2048 en entier dans la case. Le fichier étant local à l'installation, chacun
tranche pour lui-même, et le réglage du serveur ne pèse pas sur ses clients.

Aux extrêmes. Le plancher n'est pas 9 comme l'étape 4 du plan de l'audit l'écrit
(`docs/superpowers/plans/2026-09-05-deepcrate-audit.md:870`), mais 999, parce que
`abbreviate` (lignes 316 à 322) divise par mille sans autre cas : un compte de dix, abrégé, s'écrit
`0k`. Au plafond, `Integer.MAX_VALUE` veut dire ne jamais abréger, ce qui est l'intention, et le seul
dégât est un compte à cinq chiffres qui déborde sur la case voisine.

### Ce que la liste de l'audit ne dit pas

`api/module/RowModule.java:18`, `STACK_LIMIT = 16`. Deux lectures, `init/RegistryInit.java:72` où elle
devient la limite de pile de la case à rangées, et `init/RegistryInit.java:133` où elle devient la
limite de pile de l'objet lui-même. C'est le nombre qui décide de la taille maximale d'un coffre :
seize modules de rangée font passer un coffre de cuivre de trois rangées à dix-neuf, et un coffre
d'écho de huit à vingt-quatre. Un propriétaire de serveur qui trouve le mod trop généreux touche
d'abord à celui-là, avant la contenance.

Il entre dans la couche, au même titre que les quatre autres. Le plafond est 20, et il vient d'ici :
`net/CrateSortPayload.java:28` plafonne la liste de tri à 512 objets, une paire de coffres de huit
rangées avec N modules de chaque côté fait `2 * (8 + N) * 9` cases, et `(8 + N) * 18` dépasse 512 à
partir de N valant 21. Au-delà, un coffre rempli d'objets tous différents produit un paquet de tri
que le codec refuse, et la connexion tombe. Le jeu de base a son propre plafond sur la composante de
taille de pile d'un objet ; celui de DeepCrate est plus bas, donc c'est lui qui décide.

Baisser ce réglage ne rétrécit aucun coffre déjà posé. `extraRows` lit le compte réel de la pile
(`api/DeepCrateApi.java:126`), pas la limite, donc une pile de seize continue de donner seize rangées
tant qu'elle est là ; seule une insertion nouvelle est refusée. C'est la bonne moitié du
comportement, et c'est ce qui rend le réglage sûr à baisser sur un serveur qui tourne.

Deux autres candidats ont été trouvés et écartés, chacun pour une raison de code.

Les contenances des trois modules livrés, 128, 256 et 512, sont écrites dans
`init/RegistryInit.java:47` à `49`. Un propriétaire de serveur peut légitimement vouloir une
progression plus douce, et aucun pack de données ne l'atteint : une étiquette d'objets ajoute un
objet à un module existant, elle ne change pas sa contenance. Trois champs de plus suffiraient, bornés
entre 1 et 32767, avec la remarque qu'un module réglé sous la contenance de base ne fait rien du tout
puisque `capacityAmong` part de la base et prend le maximum. Écarté malgré tout : ces trois nombres
sont l'équilibrage des objets du mod et non le gouvernail d'un mécanisme, et les ouvrir revient à
ouvrir aussi les recettes, le butin et les paliers, ce que personne n'a demandé.

Les rangées des six paliers, `init/RegistryInit.java:38` à `43`, sont écartées pour une raison plus
dure : le réglage ne marcherait qu'à moitié. `alignStorageWithTier`
(`block/DeepCrateBlockEntity.java:295`) fait grandir un coffre et ne le rétrécit jamais, donc baisser
les rangées d'un palier laisse tous les coffres déjà posés à leur ancienne taille, sans rien pour le
dire. Une option qui ne s'applique qu'aux blocs futurs, silencieusement, est pire que pas d'option.

### Les nombres qui ne sont pas des réglages

Cinq constantes ressemblent à des réglages et n'en sont pas. Elles restent où elles sont, et la fiche
les nomme pour que personne n'ait à refaire le raisonnement.

`DeepCrateApi.MAX_CAPACITY` vaut `Short.MAX_VALUE` parce que la case de données écrit un short, ce que
`javap` sur `ClientboundContainerSetDataPacket` montre directement. C'est un plafond de format.
`CrateStorage.VANILLA_LIMIT` vaut 64 parce que c'est ce qu'une main porte et ce que `ItemStack.CODEC`
sait réécrire ; le baisser hacherait chaque sortie de coffre, le monter détruirait des objets à la
sauvegarde. `CrateSortPayload.MAX_ITEMS` vaut 512 parce que c'est un plafond de paquet, et il sert de
plafond au réglage des modules de rangée plutôt que d'être réglable lui-même. `CrateTier.DEFAULT_COLUMNS`
vaut 9 parce que c'est la valeur par défaut d'un constructeur d'API, qu'un palier d'addon écrase déjà
en passant sa propre largeur. Les neuf mesures de `CratePanelGeometry` sont la découpe en pixels de
`generic_54.png` et changent le dessin, pas le jeu.

## Les porteurs

Deux classes, un domaine chacune, champs seulement, dans
`mod/src/main/java/oas/dreyka/deepcrate/config/domain/`. L'ordre de déclaration est l'ordre
d'écriture sur le disque à l'intérieur d'une catégorie, donc une option ajoutée plus tard se pose à
la fin de son porteur et non au milieu.

```java
package oas.dreyka.deepcrate.config.domain;

/** What a crate holds, how far it grows, and what automation is allowed to push into it. */
public final class CrateConfig {
    private CrateConfig() {}

    /** A slot with no module in it, which is what the rest of the game holds. */
    public static int baseCapacity = 64;

    /**
     * Whether a crate answers 64 to hoppers and pipes while lithium is installed.
     *
     * Lithium replaces the hopper wholesale and keeps its own copy of the target inventory. Against a
     * container that answers more than 64 it takes items out of the hopper and never writes them in:
     * measured, eight blocks of dirt destroyed per run. Turning this off buys the feature back and
     * loses those items, which is the server owner's call rather than the mod's.
     */
    public static boolean limitAutomationWithLithium = true;

    /** Rows drawn on one page before the screen cuts the crate into several. */
    public static int maxRowsPerPage = 4;

    /** Row modules one crate takes at once, which is also the item's own stack limit. */
    public static int rowModuleStackLimit = 16;
}
```

```java
package oas.dreyka.deepcrate.config.domain;

/** What the crate screen draws. Read on the machine that draws it, never on a server. */
public final class ScreenConfig {
    private ScreenConfig() {}

    /** Past four digits a count runs out of its cell, so it is shortened and the tooltip carries the truth. */
    public static int abbreviateAbove = 999;
}
```

Le schéma les énumère par réflexion : tout champ public, statique, non final et d'un type primitif
supporté est une option, dans l'ordre de déclaration. Ajouter une option, c'est ajouter un champ, et
rien d'autre.

## Les bornes

Table de données pure, une plage par nom de champ, chaque groupe inscrivant la sienne par un rappel
pour qu'aucun groupe ne lise ni n'écrase celui d'un autre.

| option | porteur | défaut | plancher | plafond |
| --- | --- | --- | --- | --- |
| `baseCapacity` | `CrateConfig` | 64 | 1 | 32767 |
| `limitAutomationWithLithium` | `CrateConfig` | true | sans objet | sans objet |
| `maxRowsPerPage` | `CrateConfig` | 4 | 1 | 6 |
| `rowModuleStackLimit` | `CrateConfig` | 16 | 1 | 20 |
| `abbreviateAbove` | `ScreenConfig` | 999 | 999 | 2147483647 |

Un booléen traverse le serrage sans y toucher, c'est déjà le cas dans `ConfigBounds.clamp` de la
référence, et `limitAutomationWithLithium` n'a donc pas de ligne dans la table.

```java
package oas.dreyka.deepcrate.config.bounds;

import oas.dreyka.deepcrate.api.DeepCrateApi;
import oas.dreyka.deepcrate.config.BoundsRegistrar;

/** Clamp ranges for the crate options. */
public final class CrateBounds {
    private CrateBounds() {}

    public static void register(BoundsRegistrar r) {
        // Under 1, CrateStorage's constructor throws and every crate takes its chunk down with it.
        // Over MAX_CAPACITY the capacity data slot wraps, because that packet writes a short.
        r.b("baseCapacity", 1, DeepCrateApi.MAX_CAPACITY);
        // Over 6 a page is taller than the largest chest of the base game, and the player's own
        // inventory leaves the bottom of a 240-pixel screen.
        r.b("maxRowsPerPage", 1, 6);
        // Over 20 a pair of eight-row crates has more slots than CrateSortPayload.MAX_ITEMS lets the
        // sort packet name, and a crate full of distinct items kills the connection.
        r.b("rowModuleStackLimit", 1, 20);
    }
}
```

Lire `DeepCrateApi.MAX_CAPACITY` depuis une classe de bornes est sans danger, et c'est un point à ne
pas défaire par prudence mal placée. `MAX_CAPACITY` est une constante de compilation : `javac` en
recopie la valeur 32767 dans `CrateBounds.class` et aucune instruction n'y garde de référence à
`DeepCrateApi`, donc l'initialiseur statique de `DeepCrateApi`, qui appelle `FabricLoader`, ne tourne
pas. Vérifié en dehors du mod, sur une classe dont l'initialiseur statique lève une exception : la
lire par sa constante affiche la valeur sans jamais déclencher l'initialiseur. Cela compte parce que
le bloc statique de `ConfigBoundsTable` tourne dans chaque exécution de JUnit, où aucun jeu n'a
démarré.

```java
package oas.dreyka.deepcrate.config.bounds;

import oas.dreyka.deepcrate.config.BoundsRegistrar;

/** Clamp ranges for the screen options. */
public final class ScreenBounds {
    private ScreenBounds() {}

    public static void register(BoundsRegistrar r) {
        // Under 999, abbreviate() writes a count of ten as "0k": it divides by a thousand and has no
        // other case. Integer.MAX_VALUE means never shorten, which is the point of the upper end.
        r.b("abbreviateAbove", 999, Integer.MAX_VALUE);
    }
}
```

Chaque morceau prend son chemin en paramètre plutôt que de le résoudre. Seul `ConfigIo` interroge
`FabricLoader`, ce qui rend toute la lecture et toute l'écriture exerçables contre un dossier
temporaire sans jeu qui tourne. C'est la contrainte qui décide de la découpe, pas l'esthétique.

Cinq écarts par rapport aux 42 fichiers de la référence, chacun décidé et non oublié.

`ConfigFields`, la façade qui rassemble schéma, type, catégorie et accès, n'est pas reprise. Elle
existe chez LethalBreed parce que trois consommateurs la lisent, l'écran de réglages, la commande de
chat et le chargeur. DeepCrate n'a que le chargeur, et une façade à un seul consommateur est une
indirection sans emploi. Le chargeur et l'écrivain parlent directement à `ConfigSchema`,
`ConfigType`, `ConfigBounds` et `ConfigAccess`.

`ConfigCategory` n'est pas repris non plus. Chez LethalBreed, la catégorie d'une option se devine de
son nom par une liste de règles du plus précis au plus général, parce que 305 options réparties sur
onze porteurs alimentent les onglets d'un écran. Ici la catégorie est une propriété du porteur : le
schéma inscrit `CrateConfig` sous `crate` et `ScreenConfig` sous `screen`, et `ConfigSchema.categoryOf(name)`
rend la catégorie du porteur qui déclare le champ. Aucune règle à ordonner, aucun piège de premier
match, et un addon dit sa catégorie en inscrivant son porteur.

`ConfigLegacyNames`, la table des noms d'options que le mod a portés autrefois, n'est pas reprise
aujourd'hui, parce que DeepCrate n'a jamais écrit un fichier de réglages et qu'aucun nom n'a donc
jamais existé sur le disque de quelqu'un. `RenameRepair` n'a qu'une source, la distance d'édition. Le
jour où une option est renommée, cette classe est à créer avec l'ancien nom vers le nouveau, et
`RenameRepair.collect` doit la consulter avant la distance, exactement comme dans la référence : une
table explicite porte une valeur à travers un changement de vocabulaire délibéré, ce que la distance
d'édition ne sait pas faire. Ses entrées sont alors permanentes.

Le type `double[]` de `ConfigPrimitive` n'est pas repris, et avec lui disparaissent `ConfigType.csv`,
`ConfigType.copyIfArray`, la branche tableau de `ConfigApply` et celle de `ConfigWriter`. Les cinq
options sont des entiers et un booléen ; `BOOL`, `INT`, `LONG`, `DOUBLE` et `FLOAT` restent, pour
qu'ajouter une option d'un de ces types marche sans y toucher. Le danger d'avoir retiré un type est
qu'un champ d'un type non supporté n'est pas une option et disparaît sans bruit ; le test
`ConfigSchemaTest.everyFieldOnAHolderIsAnOption` ferme ce trou en faisant échouer la construction.

L'instantané des valeurs d'usine de `ConfigAccess` n'est pas repris. Il sert au bouton de remise à
zéro d'un écran de réglages et à une commande de remise à zéro, et DeepCrate n'a ni l'un ni l'autre.
`ConfigAccess` ne porte donc que `apply(name, raw, persist)`. La mise en garde du gabarit est
consignée ici pour le jour où un écran arrive : une option sans valeur d'usine relevée transforme
silencieusement son bouton de remise à zéro en bouton de corruption, et un porteur qui rejoint le
schéma après coup doit voir ses valeurs relevées au moment de son inscription.

## Le chemin d'une valeur

Une valeur écrite dans le fichier arrive au code qui la lit par cette chaîne, sans rien d'autre entre
les deux.

`config/oas/deepcrate.json` est lu par `ConfigIo.load()`, seule méthode qui résout le chemin, par
`FabricLoader.getInstance().getConfigDir().resolve("oas").resolve("deepcrate.json")`. Le plan de
l'audit propose `DeepCrateConfig.load(gameDir)` et recompose `gameDir/config/oas/...` : à ne pas
faire. `getConfigDir()` est la réponse du chargeur de mods lui-même, et rebâtir le chemin depuis le
dossier de jeu fige une hypothèse que le chargeur, lui, ne fige pas.

`ConfigLoader.load(path)` prend le chemin en paramètre. Fichier absent, il écrit les valeurs par
défaut et le dit dans le journal. Fichier présent, il l'analyse, aplatit les catégories en une table
nom vers valeur, demande à `ConfigStructure.check` ce que la forme du fichier vaut, déplace les
valeurs des noms mal orthographiés vers leur vrai nom, puis passe la main à `ConfigApply.applyAll`.
La boucle est pilotée par les champs du schéma et non par les clés du fichier, donc chaque champ est
gardé séparément et une valeur illisible ne coûte pas au joueur toutes les options qui suivent.
Chaque valeur traverse `ConfigAccess.apply`, qui analyse par `ConfigType.parse`, serre par
`ConfigBounds.clamp` et pose par `field.set(null, valeur)`. Le fichier entier est réécrit ensuite,
pour qu'une option ajoutée par une mise à jour y apparaisse d'elle-même avec sa valeur par défaut.

Le lecteur accepte aussi une option écrite à la racine, hors de sa catégorie. Chez LethalBreed cette
tolérance existe pour lire les fichiers d'avant une migration ; ici elle existe pour la main de
l'administrateur, qui ajoute une ligne sans se demander sous quel objet elle va. La réécriture la
range à sa place.

Les lignes qui changent, dans l'ordre où elles se trouvent.

`api/DeepCrateApi.java:22`, `public static final int BASE_CAPACITY = 64;` disparaît. Ligne 163,
`return crateModule == null ? BASE_CAPACITY : crateModule.capacity();` devient
`CrateConfig.baseCapacity`. Ligne 172, `int capacity = BASE_CAPACITY;` devient
`int capacity = CrateConfig.baseCapacity;`. Ligne 40, `AUTOMATION_LIMITED` disparaît au profit de la
méthode décrite plus bas.

`block/DeepCrateBlockEntity.java:36`,
`new CrateStorage(CrateTier.DEFAULT_COLUMNS, DeepCrateApi.BASE_CAPACITY)` devient
`new CrateStorage(CrateTier.DEFAULT_COLUMNS, CrateConfig.baseCapacity)`.

`inventory/CrateStorage.java:77`, `return DeepCrateApi.AUTOMATION_LIMITED ? Math.min(limit, VANILLA_LIMIT) : limit;`
devient `return DeepCrateApi.automationLimited() ? Math.min(limit, VANILLA_LIMIT) : limit;`.

`api/CrateLayout.java:10`, `public static final int MAX_ROWS_PER_PAGE = 4;` disparaît. Ligne 13,
`int pageCount = Math.max(1, (rows + MAX_ROWS_PER_PAGE - 1) / MAX_ROWS_PER_PAGE);` lit
`CrateConfig.maxRowsPerPage` dans une variable locale, une seule fois, parce que la lire deux fois
dans la même expression laisserait une fenêtre où les deux lectures diffèrent. Le paquet `api` se met
à dépendre de `config.domain`, dans ce sens et seulement dans ce sens : un porteur n'importe rien,
donc la dépendance s'arrête là et ne boucle pas.

`api/module/RowModule.java:18`, `public static final int STACK_LIMIT = 16;` disparaît.
`init/RegistryInit.java:72`, `RowModule.STACK_LIMIT` devient `CrateConfig.rowModuleStackLimit`, et de
même ligne 133 dans `new Item.Properties().stacksTo(...)`.

`client/screen/DeepCrateScreen.java:47`, `private static final int ABBREVIATE_ABOVE = 999;` disparaît,
et son commentaire part sur le champ du porteur. Les lignes 265 et 281 lisent
`ScreenConfig.abbreviateAbove`.

Quatre fichiers de test suivent. `mod/src/test/java/oas/dreyka/deepcrate/CrateLayoutTest.java:31`
lit `CrateConfig.maxRowsPerPage` au lieu de `CrateLayout.MAX_ROWS_PER_PAGE`.
`mod/src/gametest/java/oas/dreyka/deepcrate/gametest/CrateMenuGameTest.java:31` lit

### L'ordre du chargement

`DeepCrateMod.onInitialize` devient ceci, et l'ordre compte.

```java
    @Override
    public void onInitialize() {
        AddonInit.registerConfig();
        DeepCrateConfig.load();
        RegistryInit.register();
        AddonInit.register();
        CreativeTabInit.register();
        CrateSortPayload.register();
        ConfigNotice.register();
    }
```

Deux contraintes se croisent, et elles ne laissent qu'une place à `load()`.

L'inscription des porteurs vient avant la lecture du fichier, parce que le chargeur laisse tomber ce
qu'il ne reconnaît pas et que la réécriture qui suit efface la ligne. `ConfigSchema` inscrit ses deux
porteurs dans son propre bloc statique ; un addon inscrit le sien pendant `AddonInit.registerConfig()`,
d'où ce premier passage.

La lecture du fichier vient avant `RegistryInit.register()`, parce que c'est là que
`rowModuleStackLimit` est lu, et il est lu depuis l'initialisation de la classe. Ligne 72, dans le
bloc statique, pour la limite de pile de la case à rangées. Ligne 133, atteinte depuis le champ
statique `ROW_MODULE_ITEM` de la ligne 58, pour celle de l'objet. Toucher `RegistryInit` déclenche les
deux d'un coup, et `register()` est justement ce qui la touche. Le plan de l'audit place `load()` en
première ligne (`plans/2026-09-05-deepcrate-audit.md:897`) en donnant pour raison que le palier lit la
contenance de base : la raison est fausse, `RegistryInit` inscrit des modules à contenance fixe, mais
la position est la bonne pour une autre raison, celle-ci.

La question se pose pour chacune des cinq, pas seulement pour celle qui a failli passer.

| option | site de lecture | ce qui déclenche cette lecture |
| --- | --- | --- |
| `baseCapacity` | `DeepCrateApi.java:163` et `:172`, `DeepCrateBlockEntity.java:36` | un module déplacé dans sa case, un bloc entité construit |
| `limitAutomationWithLithium` | `DeepCrateApi.automationLimited()`, appelée depuis `CrateStorage.java:77` | une trémie qui pousse, case par case et tick par tick |
| `maxRowsPerPage` | `CrateLayout.java:13` | `DeepCrateApi.layoutFor` (`DeepCrateApi.java:191` et `:202`), appelée depuis `DeepCrateBlockEntity.java:190` et `:201` à l'ouverture |
| `rowModuleStackLimit` | `RegistryInit.java:72` et `:133` | l'initialisation de la classe `RegistryInit` |
| `abbreviateAbove` | `DeepCrateScreen.java:265` et `:281` | une image dessinée par le client |

Quatre de ces sites demandent un monde chargé ou une fenêtre ouverte, donc bien après le point
d'entrée. La ligne 36 du bloc entité ressemble à un initialiseur statique et n'en est pas un : c'est
un champ d'instance, il tourne à la construction, et aucun bloc entité n'est construit pendant
`onInitialize`. Le cinquième site est le seul du temps d'initialisation, et c'est lui qui décide de
l'ordre ci-dessus.

Le premier passage sur les addons est une méthode par défaut de plus sur l'interface qui existe déjà,
sans nouveau point d'accroche dans `fabric.mod.json` :

```java
@FunctionalInterface
public interface DeepCrateAddon {
    /**
     * Config holders and clamp groups, and nothing else. It runs before the file is read, which is
     * before a single registry is filled: reaching RegistryInit from here runs its class initialiser
     * ahead of the load and freezes rowModuleStackLimit at its default.
     */
    default void onDeepCrateConfig() {}

    void onDeepCrateInit();
}
```

```java
    /** Held between the two passes so an addon is the same object in both. */
    private static List<DeepCrateAddon> addons = List.of();

    public static void registerConfig() {
        addons = FabricLoader.getInstance().getEntrypoints(DeepCrate.MOD_ID, DeepCrateAddon.class);
        for (DeepCrateAddon addon : addons) {
            addon.onDeepCrateConfig();
        }
    }

    public static void register() {
        for (DeepCrateAddon addon : addons) {
            addon.onDeepCrateInit();
        }
    }
```

La liste est retenue plutôt que redemandée, pour qu'un addon qui garde un état entre ses deux méthodes
le retrouve, sans dépendre de ce que le chargeur met en cache. Un addon sans réglage ne redéfinit rien
et ne voit pas la différence ; celui qui en a écrit inscrit son porteur du bon côté :

```java
    @Override
    public void onDeepCrateConfig() {
        ConfigSchema.registerHolder(MyAddonConfig.class, "myaddon");
        ConfigBounds.registerGroup(MyAddonBounds::register);
    }
```

Ce que la méthode par défaut demande en échange est une règle, pas une garantie du compilateur : le
premier passage ne doit toucher aucune classe du mod hors du paquet `config`. Le commentaire de
l'interface la porte à l'endroit où on la lit, et c'est le seul endroit du mod où l'ordre tient à un
contrat plutôt qu'à une suite d'appels.

## Sortir AUTOMATION_LIMITED du chargement de classe

La constante répond à la mauvaise question. Elle dit si lithium est là, quand ce qu'il faut savoir est
si lithium est là et si l'administrateur veut la bride. Dans l'ordre décidé plus haut, un champ
`static final` s'en tirerait : `RegistryInit.register()` est ce qui touche `DeepCrateApi` en premier,
donc après la lecture du fichier, et la valeur serait juste. Elle serait juste par accident. Rien ne
l'empêche de basculer le jour où une classe du paquet `config` appelle une méthode de `DeepCrateApi`
au lieu d'en lire la constante `MAX_CAPACITY`, qui, elle, ne déclenche aucune initialisation.

Le remplacement tient en deux morceaux.

```java
    /** The mod list never changes while the game runs, so this one really is decided once. */
    private static final boolean LITHIUM_PRESENT = FabricLoader.getInstance().isModLoaded("lithium");

    /**
     * Whether automation may go past a vanilla stack.
     *
     * Lithium replaces the hopper wholesale and keeps its own copy of the target inventory. Against a
     * container that answers more than 64 it takes items out of the hopper and never writes them in:
     * measured, eight blocks of dirt destroyed per run. Telling automation 64 in that case costs the
     * feature and keeps the items; the player's own hands are unaffected, they go through the menu.
     */
    public static boolean automationLimited() {
        return CrateConfig.limitAutomationWithLithium && LITHIUM_PRESENT;
    }
```

La sonde lithium reste figée au chargement de classe, et c'est correct : la liste des mods est close
avant qu'un point d'entrée tourne et ne change plus de la partie. Le réglage, lui, est relu à chaque
appel. Rien à rafraîchir après la lecture du fichier, rien à se rappeler d'appeler le jour où une
commande de rechargement arrive, et aucun moment où un champ mis en cache dirait autre chose que le
fichier.

Le coût sur le chemin chaud est celui de deux lectures de champ statique et d'un et logique, contre
une lecture de champ aujourd'hui. La tâche 10 de l'audit, qui vise ce même chemin, n'a donc rien à
reprendre ici. La solution qu'il ne faut pas retenir est celle qui appelle `isModLoaded` à chaque
lecture : `automationCapacityFor` est appelée par case et par tick de trémie, et le hachage d'une
chaîne à cet endroit se paie.

## Ce que deviennent les constantes publiques

Quatre constantes publiques disparaissent : `DeepCrateApi.BASE_CAPACITY`,
`DeepCrateApi.AUTOMATION_LIMITED`, `CrateLayout.MAX_ROWS_PER_PAGE` et `RowModule.STACK_LIMIT`. La
question de les garder dépréciées se pose, et la réponse tient à un détail de compilation qui les
sépare en deux groupes.

`javap -p -constants` sur les classes déjà compilées du mod montre lesquelles :

```
  public static final int BASE_CAPACITY = 64;
  public static final int MAX_CAPACITY = 32767;
  public static final boolean AUTOMATION_LIMITED;
```

`BASE_CAPACITY` porte sa valeur dans l'attribut `ConstantValue`, `AUTOMATION_LIMITED` non, parce que
son initialiseur n'est pas une expression constante. La conséquence se vérifie au bytecode : une
classe qui lit une constante de compilation compile en `bipush 64`, une classe qui lit l'autre
compile en `getstatic`.

Garder `BASE_CAPACITY`, `MAX_ROWS_PER_PAGE` et `STACK_LIMIT` en constantes dépréciées ne servirait
donc à rien de bon. Un addon compilé contre elles porte déjà 64, 4 et 16 recopiés dans son propre
fichier de classe, et continuera de les porter quoi que nous fassions du champ : il ne verra jamais
le réglage de l'administrateur, et il calculera silencieusement des contenances et des découpes qui
ne sont pas celles du serveur. Une constante gardée par compatibilité serait une compatibilité avec
un mauvais nombre. Les retirer transforme la même erreur en erreur de compilation, que l'auteur de
l'addon voit et corrige en une ligne.

`AUTOMATION_LIMITED` est le cas inverse : un addon la lit par `getstatic`, donc un champ non final
tenu à jour marcherait. Elle est retirée quand même, par cohérence et parce qu'un champ ne sait pas
dire "le réglage et lithium" sans que quelqu'un pense à le réassigner après chaque lecture du
fichier. `automationLimited()` le dit sans rien à retenir.

Ce qui rend ces retraits acceptables : le mod n'est pas publié. `mod/gradle.properties` porte
`mod_version=1.0.0`, `store/curseforge.md` et `store/modrinth.md` sont des brouillons non suivis par
git, et aucun addon n'existe. Le coût est nul aujourd'hui et il ne le sera plus dans un mois.

`DeepCrateApi.MAX_CAPACITY` reste, et reste une constante de compilation. C'est un plafond de format,
il ne bougera pas tant que le paquet écrira un short, et un addon a raison de le recopier chez lui.

Le README porte deux ajouts, en anglais comme le reste du fichier. Une section `## Settings` entre
`## Hoppers` et `## For other mods`, qui nomme le chemin du fichier et les cinq options avec leur
plage. Deux phrases dans `## For other mods`, puisque c'est la section qu'un auteur d'addon lit : les
quatre constantes retirées avec ce qui les remplace, et `onDeepCrateConfig()` avec la règle qui va
avec, un porteur inscrit là et rien d'autre touché là. Les deux pages de boutique décrivent le
comportement avec lithium en encadré ; une phrase leur manque désormais, celle qui dit qu'un
propriétaire de serveur peut revenir dessus.

## Le fichier sur le disque

Écriture atomique, dans un fichier temporaire puis renommage, avec repli sur un remplacement simple
quand le système de fichiers refuse le renommage atomique. Un plantage en cours d'écriture laisserait
sinon un fichier tronqué et aucun retour possible.

Options groupées sous leur catégorie, catégories triées par ordre alphabétique, options gardant
l'ordre du schéma à l'intérieur d'une catégorie. Le fichier est réécrit à chaque lancement, et un
ordre non déterminé produirait un diff neuf à chaque fois, ce qui apprend à ne plus lire les diffs.

```json
{
  "crate": {
    "baseCapacity": 64,
    "limitAutomationWithLithium": true,
    "maxRowsPerPage": 4,
    "rowModuleStackLimit": 16
  },
  "screen": {
    "abbreviateAbove": 999
  }
}
```

Les valeurs gardent leur type JSON naturel et le nom exact du champ, ce qui est ce qui rend le fichier
modifiable à la main, et c'est le but.

## Quand le fichier est faux

Trois cas, trois réponses, et aucune ne perd ce que l'administrateur a tapé.

Un nom qui ne correspond à aucune option est réparé quand la réparation ne demande pas de deviner.
La source est la distance d'édition, avec un budget qui grandit avec la longueur du nom, et la
décision attend que le fichier entier soit lu : deux fautes qui convergent vers une même option sont
aussi ambiguës qu'une faute entre deux options. Une réparation ne vise jamais une option que le
fichier porte déjà par ailleurs. Ce qui ne se répare pas est signalé avec le nom réel le plus proche,
ou sans rien quand rien n'est proche, parce qu'une supposition en l'air est pire que pas de
supposition.

Un fichier qui ne s'analyse pas, ou qui s'analyse sans porter une seule option reconnaissable, est
écarté sous un suffixe daté et un fichier neuf est écrit à sa place. L'archive est élaguée à trois
entrées. L'administrateur garde le contenu et le serveur démarre. Le rapport de la lecture n'est pas
rendu dans ce cas : il décrit un fichier qui vient d'être déplacé, et râler pendant toute la session
au sujet d'un fichier qui n'existe plus est pire que se taire.

Une valeur hors de sa plage est serrée, silencieusement et volontairement, puis la réécriture pose la
valeur serrée sur le disque. C'est le second point qui compte : sans lui, le 99999 refusé revient au
lancement suivant et l'administrateur croit que son réglage marche.

## Ce que l'opérateur voit

Une ligne de journal seule ne vaut à peu près rien, un joueur solo n'ouvre jamais `latest.log`. Le
rapport de la dernière lecture est gardé dans `ConfigIo.lastReport()` et montré à un opérateur quand
il se connecte, seulement pour ce sur quoi il peut agir, c'est-à-dire une clé dont la valeur est
perdue ou une clé écrite deux fois. Ce que la réécriture corrige toute seule reste muet.

`init/ConfigNotice.java` inscrit l'écoute sur `ServerPlayConnectionEvents.JOIN`, garde derrière la
même permission que les commandes d'opérateur, et écrit au plus six lignes avant de dire combien il
en reste. Cinq clés, dont celle de ce reste, dans les deux fichiers de langue, mêmes places de format
des deux côtés.

```json
  "deepcrate.notice.config_problems": "%s problem(s) in the structure of config/oas/deepcrate.json:",
  "deepcrate.notice.unknown_option": "  '%s' matches no option.",
  "deepcrate.notice.unknown_ambiguous": "  '%s': did you mean '%s'? Too ambiguous to repair on its own.",
  "deepcrate.notice.duplicated": "  '%s' is written in two categories, only one copy is read.",
  "deepcrate.notice.more_lines": "  and %s more, in latest.log."
```

```json
  "deepcrate.notice.config_problems": "%s problème(s) dans la structure de config/oas/deepcrate.json :",
  "deepcrate.notice.unknown_option": "  '%s' ne correspond à aucune option.",
  "deepcrate.notice.unknown_ambiguous": "  '%s' : vouliez-vous '%s' ? Trop ambigu pour être corrigé tout seul.",
  "deepcrate.notice.duplicated": "  '%s' est écrit dans deux catégories, une seule copie est lue.",
  "deepcrate.notice.more_lines": "  et %s de plus, dans latest.log."
```

La cinquième ne s'écrit que s'il reste quelque chose : à six problèmes ou moins, l'opérateur voit les
six et rien après.

## Les tests

Quatre fichiers, tous en JUnit ordinaire. La couche de réglages ne touche aucun type de Minecraft,

### ConfigLoaderTest

`mod/src/test/java/oas/dreyka/deepcrate/config/io/ConfigLoaderTest.java`. Les options sont des
champs statiques, donc un test qui en laisse un modifié décide de ce que le suivant lit ; le relevé
et la remise en place encadrent chaque test par réflexion sur le schéma, sans recopier les valeurs
par défaut.

```java
package oas.dreyka.deepcrate.config.io;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertTrue;

import oas.dreyka.deepcrate.config.domain.CrateConfig;
import oas.dreyka.deepcrate.config.domain.ScreenConfig;
import oas.dreyka.deepcrate.config.schema.ConfigSchema;
import java.lang.reflect.Field;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.stream.Stream;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.io.TempDir;

/**
 * The read path, against a temporary directory. Reachable with no game running because
 * ConfigLoader takes its path: ConfigIo is the only class that asks FabricLoader where the file is.
 */
class ConfigLoaderTest {
    @TempDir Path dir;

    private final Map<String, Object> held = new LinkedHashMap<>();

    @BeforeEach
    void hold() throws Exception {
        for (Field field : ConfigSchema.all()) {
            held.put(field.getName(), field.get(null));
        }
    }

    @AfterEach
    void putBack() throws Exception {
        for (Field field : ConfigSchema.all()) {
            field.set(null, held.get(field.getName()));
        }
    }

    private Path write(String json) throws Exception {
        Path file = dir.resolve("deepcrate.json");
        Files.writeString(file, json);
        return file;
    }

    @Test
    void anAbsentFileIsWrittenWithTheDefaults() throws Exception {
        Path file = dir.resolve("deepcrate.json");

        assertNull(ConfigLoader.load(file), "there was no file to have anything wrong with it");

        assertTrue(Files.exists(file));
        assertTrue(Files.readString(file).contains("baseCapacity"), "the fresh file must hold the schema");
        assertEquals(64, CrateConfig.baseCapacity);
    }

    @Test
    void aValueOutsideItsRangeIsClampedOnDiskToo() throws Exception {
        Path file = write("{\"crate\":{\"baseCapacity\":99999}}");

        ConfigLoader.load(file);

        assertEquals(32767, CrateConfig.baseCapacity);
        // Without this half, the refused 99999 is still in the file and comes back on the next
        // launch, and the admin watches a setting that never takes.
        assertTrue(Files.readString(file).contains("32767"));
    }

    @Test
    void anUnparseableFileIsSetAsideAndItsBytesSurvive() throws Exception {
        Path file = write("{ this is not json");

        assertNull(ConfigLoader.load(file), "the config now running is the defaults, so there is nothing to warn about");

        assertTrue(Files.exists(file), "a fresh default file must be written in its place");
        Path archive;
        try (Stream<Path> listing = Files.list(dir)) {
            archive = listing.filter(p -> p.getFileName().toString().contains(".old-")).findFirst().orElseThrow();
        }
        assertTrue(Files.readString(archive).contains("this is not json"),
                "the archive must be the original bytes, not a rewrite");
        assertEquals(64, CrateConfig.baseCapacity);
    }

    @Test
    void aFileWhoseKeysAreAllStrangersIsSetAside() throws Exception {
        Path file = write("{\"Nonsense\": 1, \"AlsoNonsense\": 2}");

        assertNull(ConfigLoader.load(file));

        try (Stream<Path> listing = Files.list(dir)) {
            assertTrue(listing.anyMatch(p -> p.getFileName().toString().contains(".old-")));
        }
    }

    @Test
    void aMisspelledOptionIsReadAndRewrittenUnderItsRealName() throws Exception {
        Path file = write("{\"crate\":{\"baseCapcity\":128}}");

        ConfigLoader.load(file);

        assertEquals(128, CrateConfig.baseCapacity, "the value on the misspelled line must reach the real option");
        String rewritten = Files.readString(file);
        assertTrue(rewritten.contains("baseCapacity"));
        assertFalse(rewritten.contains("baseCapcity"), "the typo must be gone from the file");
    }

    @Test
    void anOptionTheFileDoesNotCarryComesBackWithItsDefault() throws Exception {
        Path file = write("{\"crate\":{\"baseCapacity\":128}}");

        ConfigLoader.load(file);

        assertEquals(999, ScreenConfig.abbreviateAbove);
        assertTrue(Files.readString(file).contains("abbreviateAbove"),
                "an option added by an update has to appear by itself, or nobody knows it exists");
    }
}
```

Le cinquième test mérite un mot, parce qu'il pourrait devenir faux tout seul. `baseCapcity` est à une
suppression de `baseCapacity`, donc dans le budget de la distance d'édition, et aucune autre option
n'est aussi proche. Le jour où une sixième option porte un nom voisin, la réparation devient ambiguë
et ce test échoue en le disant, ce qui est le comportement voulu et non une régression.

`mod/src/test/java/oas/dreyka/deepcrate/config/io/ConfigWriterTest.java`, trois cas. Chaque option
